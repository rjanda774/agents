# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository shape

This repo currently holds two unrelated, independently-runnable projects, plus a couple of stray scripts:

- **Root (`app.py`, `requirements.txt`, `foundations/`)** — the deployed Hugging Face Space: a Gradio chat app where an LLM answers questions in character as the repo owner, using their LinkedIn profile/summary as context (`foundations/app.py`, class `Me`). This is intentionally minimal — a previous restructuring ("HF deploy") stripped the rest of the original course repo (the numbered `1_foundations`...`5_autogen` lab folders and their `community_contributions`) down to just this, to keep the deployed Space small.
- **`6_mcp/`** — a separate, self-contained project: an autonomous agent-driven paper-trading floor (currently a single trader, Cathie, who trades options credit spreads). Deliberately kept out of the HF-deploy trim (unlike the other numbered folders) because it's the active project. Everything below is about this directory.
- `LEANscriptOptionsbacktest.py`, `pdf_to_text.py` — standalone one-off utility scripts at root, unrelated to either app above.

`6_mcp/community_contributions/` (a grab-bag of unrelated student/community submissions bundled with the original course material) has been removed. There is no root README, no lint config, and no test suite.

## Running things

**HF chat app** (root): `python app.py` — needs `OPENAI_API_KEY`; reads `foundations/me/ProfileLinkedin.txt` and `foundations/me/summaryRJ.txt`.

**Trading floor** (`6_mcp/`), each run from inside `6_mcp/`:
- `uv run reset.py` — resets Cathie's stock account (cash/strategy text; she never actually trades stocks, see below) back to its starting balance (wipes prior state).
- `uv run reset_cathie_options.py` — separately resets Cathie's *options* account (`cathie_options` in `accounts.db`): clears open/closed spread positions and resets cash to $10,000. Run this too when you want a clean slate, since options positions live in a separate pseudo-account from the stock one `reset.py` touches.
- `uv run trading_floor.py` — starts the scheduler: runs every trader once, then sleeps `RUN_EVERY_N_MINUTES` (default 60) and repeats. Skips runs while the market is closed unless `RUN_EVEN_WHEN_MARKET_IS_CLOSED=true`.
- `uv run app.py` — Gradio dashboard visualizing account state/logs across traders.
- `python install_options_deps.py` — installs `yfinance`/`optionlab`/`scipy` (the options system's dependencies; not needed by anything else in `6_mcp/`).
- Individual MCP servers (`accounts_server.py`, `push_server.py`, `market_server.py`, `regime_server.py`, `options_trading_wrapper.py`) are not run directly — they're launched as subprocesses over stdio by the trading floor per `mcp_params.py`.

`6_mcp/pyproject.toml` + `uv.lock` declare/pin the subproject's dependencies (including `yfinance`/`optionlab`/`scipy`, previously undeclared anywhere) -- restored after being removed along with the rest of the original course scaffolding in the HF-deploy restructuring; `uv run <script>.py`/`uv sync` from inside `6_mcp/` now resolve and sync a `.venv` from that lock rather than falling back to ad-hoc-script mode. `python install_options_deps.py` still exists and still works as a standalone manual-`pip install` path for anyone managing their own environment directly instead of through uv (e.g. `python <script>.py` against an existing venv they already maintain by hand) -- both are equally supported ways to run this subproject, pick whichever fits how you're already working. Note that the trading floor's own MCP-server subprocesses (`accounts_server.py` etc.) are deliberately launched with `sys.executable`, not `uv run`, regardless of this manifest -- see `mcp_params.py`'s `PYTHON` comment; that's about guaranteeing the exact same interpreter/env as the parent process, not about the lock file.

**On the `openai-agents`/`mcp` version gap**: the user's actually-installed `openai-agents` has historically lagged `uv.lock`'s pinned version significantly (see PR #4's `accounts_client.py` regression, where an SDK method assumed present on the newer pinned version didn't exist on the older installed one). Investigating upgrade feasibility surfaced a second, harder version-gap risk one layer down: `uv.lock`'s pinned `openai-agents` transitively resolves `mcp>=2.0`, and `mcp` 2.0 renamed `mcp.server.fastmcp.FastMCP` to `mcp.server.mcpserver.MCPServer` (moved module, no back-compat alias left anywhere in the package) -- confirmed by diffing both versions' wheels and by installing each into a real venv and importing a real server file against both. Every one of this codebase's five `*_server.py` files imported `FastMCP` from the old path directly, which would have failed at import time (`ModuleNotFoundError`, not the friendlier `AttributeError` class of failure PR #4 hit) the moment `mcp` got upgraded to 2.x -- a harder failure than a missing-method gap, since it kills the server subprocess before any of that file's own code (including any hasattr-style guard) can run. `mcp_compat.py` now provides `FastMCP` as a try/except shim (new path first, old path as fallback) that all five server files import from instead of importing `mcp.server.fastmcp` directly, verified end-to-end against real `mcp==1.19.0` and `mcp==2.0.0` installs -- the rest of the class's API this codebase touches (constructor's `name` param, `.tool()`, `.resource()`, `.run(transport="stdio")`) was otherwise unchanged between the two. Separately, `openai-agents>=0.21` also transitively pulls `openai>=3.0`, whose one breaking change is HTTPX2 replacing `httpx` as the default HTTP client, including a switch from `certifi`'s bundled CA bundle to the OS trust store for TLS verification -- this codebase's own `AsyncOpenAI(base_url=..., api_key=...)` usage (`traders.py`, for the OpenRouter/DeepSeek/Grok/Gemini gateways) is exactly the "SDK's default HTTP client" case openai's own migration guide says needs no code changes, but the OS-trust-store switch is an environment-dependent risk (Windows machine, any corporate/proxy TLS interception) that can only be confirmed by actually running on the target machine, not from a code review.

## Architecture: the trading floor (`6_mcp/`)

A single trader persona, Cathie (named for Cathie Wood; aggressive crypto ETF bets), runs each cycle (`trading_floor.py` → `traders.py`). The floor originally ran four personas (Warren/Buffett-value, George/Soros-macro, Ray/Dalio-risk-parity, plus Cathie); the other three were removed to simplify things, but `traders.py`/`trading_floor.py` still support an arbitrary list of traders via `names`/`lastnames`/`model_names` — add entries there and a matching strategy in `reset.py` to bring more traders back.

Persona strategy text lives in `reset.py`; it's injected verbatim into the agent's prompt (`templates.py`) alongside live account state.

Cathie's named ETF universe (`universe.py: CATHIE_ETF_UNIVERSE`) is the one place that list of tickers is defined; `reset.py`'s strategy text and both `templates.py` prompts (`trader_instructions`, `new_trades_message`) all interpolate it rather than hand-copying their own list -- they used to, and the copies had already drifted apart (one silently dropped four tickers). Her Researcher sub-agent gets explicit instruction (in both `researcher_instructions` and the trader-facing prompts) to check its per-trader memory for recently-suggested underlyings and favor genuinely different candidates over defaulting to the same familiar few -- prompt steering only, same caveat as everything else non-server-enforced in this file.

- **Model selection**: Cathie uses `gpt-4o-mini` by default, overridable via `MODEL_NAME` (`trading_floor.py`).
- **Two tool surfaces per trader** (`traders.py: Trader.create_agent`): its own "trader" MCP servers (accounts, push notifications, market data, and — Cathie only — the regime signal tool), plus a `Researcher` sub-agent exposed as a callable `Tool`, which has its own MCP servers (web fetch, Brave search, and a per-trader libsql memory store) for qualitative news research (`mcp_params.py`). `traders.py` itself also reads the accounts server directly each cycle (account report, strategy text) via `accounts_client.py`, outside of the LLM's own tool calls; it does this through the same persistent `accounts_server` connection already open for the cycle (looked up by name off `trader_mcp_servers`, see `run_agent`), rather than `accounts_client.py` spawning a fresh subprocess+handshake per read — `accounts_client.py`'s functions still support the latter as a fallback for one-off calls outside a trading cycle (e.g. from a notebook).
- **Trade vs. rebalance**: `Trader.run()` alternates each cycle between `trade_message` (look for new opportunities) and `rebalance_message` (review existing positions), via the `self.do_trade` flip (`templates.py`). Options traders (Cathie) are the exception -- see below.
- **Persistence**: account state and logs live in a local SQLite DB (`database.py`, `accounts.py`), read/written concurrently by `trading_floor.py` and the `app.py` dashboard when both run at once.
- **Scheduler robustness**: `trading_floor.py`'s main loop and `traders.py: Trader.run()`'s post-cycle portfolio-value recording (`Account.get`/`read_account`/`account.save`, all SQLite I/O) both fail safe on error now rather than crashing the whole process -- `is_market_open()` (`market.py`) catches Polygon errors and reports the market closed for that cycle; the portfolio-value tail catches its own errors (e.g. a locked DB from the dashboard's concurrent access) and just skips that cycle's chart data point. Both used to be unguarded code sitting directly in the scheduler's per-cycle path outside any trader-level try/except, so either one throwing took the entire floor down permanently until manually restarted.
- **Market data tier**: `market.py` picks between free EOD-only, paid 15-min-delayed, or realtime data based on `POLYGON_PLAN`; the "market" MCP server swaps between a local `market_server.py` (free tier) and the full `mcp_polygon` package (paid/realtime), per `mcp_params.py`.

**Cathie's regime-signal tool** (`regime_signal.py` / `regime_server.py`, wired in via `mcp_params.py: TRADERS_WITH_REGIME_TOOL`) is a quantitative addition on top of the otherwise fully LLM-reasoning-driven traders:
- Labels each day Bull/Sideways/Bear from a *rolling* 20-day cumulative return (needs a rolling window to have a live "today" label).
- Fits the transition matrix from *non-overlapping* 20-day strides rather than daily — adjacent rolling windows share 19/20 days of underlying data, so counting daily transitions as independent samples overstates confidence (pseudo-replication).
- Forecasts N-days-ahead regime probabilities via true matrix exponentiation (`numpy.linalg.matrix_power`), not by squaring a single scalar probability — squaring a scalar silently assumes zero autocorrelation, which contradicts the tool's own "stickiness"/persistence concept.
- Reports an explicit `confidence` label tied to transition-matrix sample size, and refuses to return a signal at all below a minimum history threshold rather than guessing.
- It's framed to Cathie (in her `reset.py` strategy text and `templates.py` instructions) as a *lagging* trend-context signal to weigh alongside her news research when picking directional bias — not a standalone buy/sell instruction, and not a profitability guarantee.
- **Fixed bug: a regime that never occurred as a source state in the strided samples silently reported `persistence=0.0` and an invalid (non-normalized) forecast.** `build_transition_matrix`'s stride-sampling can leave one state's row of the transition matrix all zeros — that state simply never appeared as a transition-*from* state among the (sparser) strided samples used to fit the matrix, even though it occurs in the full daily series. That's a stochastic-matrix violation: reading `matrix[state][state]` off a zero row gives a literal `0.0`, indistinguishable from "this regime provably never repeats" even though the real situation is "zero samples, no evidence either way" — and `numpy.linalg.matrix_power` on a zero row produces forecast probabilities that don't sum to 1. Found via synthetic-data testing while verifying the tool against a live Polygon key (no live key was needed to reproduce it — it's a pure logic bug). `build_transition_matrix` now also returns per-row sample counts; `get_regime_signal` checks today's regime's row before trusting it and returns an explicit "zero observed transitions from this regime" error instead, consistent with the existing overall-history refusal above.

**Cathie's options credit-spread system** is her actual trading mechanism — she does not buy/sell stocks at all (`templates.py: trader_instructions` forbids it explicitly; enforced by instruction, not by removing her `accounts_server` access, since she still needs `get_balance`/`change_strategy`). It's a separate, more substantial subsystem:
- **`options_models.py`** — `CreditSpread`/`OptionLeg`/`OptionsAccount` pydantic models. Positions are tracked in a pseudo-account named `cathie_options` in the same `accounts.db` (via `database.py: read_account`/`write_account`), completely separate from her real `cathie` stock `Account` (which stays untouched at its starting balance, since she never trades stocks).
- **`options_trading_server.py`** (run via `options_trading_wrapper.py`, an MCP-tool wrapper) — five tools: `get_options_chain` and `analyze_credit_spread` (read-only: real chains/Greeks from `yfinance`, P/L and probability-of-profit via `optionlab`'s Black-Scholes), `sell_credit_spread` and `close_credit_spread` (mutate `cathie_options`), `get_options_positions` (read it back). Only trades **bull put** and **bear call** credit spreads — defined-risk, premium-selling strategies — never naked options.
- **Server-enforced rules** (rejected outright by `sell_credit_spread`, not just requested by prompt): 25–45 day expirations only, max loss capped at 3% of the options account's current cash (`OptionsAccount.cash` in `options_models.py`, credited/debited on open/close), a $100 minimum net premium per trade, and short-leg delta magnitude under 0.20 (raised from 0.15 to qualify more candidate strikes, accepting a somewhat higher assignment/breach probability and lower win rate per trade in exchange; real delta computed via Black-Scholes in both `get_options_chain` and `analyze_credit_spread` -- yfinance's raw chain has no delta column at all, so this check was previously silently unenforceable and let ITM-prone strikes through). `close_credit_spread` is gated the same way -- it verifies against live data that one of its three exit conditions (75%+ profit captured, short strike breached, ≤7 days to expiration) is actually true before closing anything, and rejects the call otherwise; it no longer trusts the LLM's self-reported `reason`, after positions were observed being closed within minutes of opening for no valid trigger. Everything else -- minimum probability-of-profit, *when* to check positions each cycle -- is prompt-only guidance in `templates.py`'s Cathie-specific `trader_instructions`/`close_positions_message`/`new_trades_message`, which the LLM has been observed to not always follow exactly (e.g. opening spreads below the stated premium floor before it was moved server-side); treat those as strong steering, not guarantees, unless/until they're moved server-side too.
- **Known gap (prompt-only, not server-enforced): the LLM has been observed narrating a close_credit_spread rejection as a success.** A rejection returns an ordinary-looking `{"error": ...}` JSON payload rather than raising an exception, and a live case was caught where the model's own stated `reason` cited grounds that map to both self-checkable triggers being false (`"DTE > 7 days, no strikes breached"` -- i.e. neither expiry nor breach applies, and no profit claim was made either), the position was confirmed still open via a follow-up `get_options_positions()` call in the same trace, yet the model's final summary *and* its push notification both reported a successful $215 close. `templates.py`'s `trader_instructions` and `close_positions_message` now explicitly instruct checking for `"status": "POSITION CLOSED"` vs. an `"error"` key before reporting or notifying anything -- but like the premium-floor case above, this is prompt steering, not a guarantee. Worth periodically spot-checking real trace logs against `get_options_positions()`/the DB rather than trusting the model's own narration or push notifications at face value.
- **Fixed bug: `close_credit_spread` trusted a 0/0 bid-ask quote as a real $0.00 closing cost.** The profit-capture check (`closing_cost <= 25% of premium`) used whatever `yfinance` returned for the short/long legs without checking it was a real quote. `yfinance` returns `bid=0, ask=0` when no market maker has an active price -- routine outside regular trading hours, or for a thin/deep-OTM strike -- not proof the option is actually worthless. That meant a stale overnight quote could silently compute a fabricated $0.00 closing cost, which trivially satisfies the 75%-captured rule and force-closes a position that was never verified against a real price. At least two live positions closed for suspiciously "perfect" $0.00 cost shortly after opening, both outside regular trading hours (no real session elapsed in between) -- the kind of theta decay that would take weeks, not hours, on a 25-45 DTE spread. Now requires at least one nonzero side (bid or ask) on *each* leg before trusting the quote; otherwise falls through to the existing "no market data" handling, which assumes breakeven rather than fabricating a gain. This does not retroactively correct any already-closed position's recorded P&L in the DB -- those entries stand as recorded unless manually corrected.
- **Fixed bug: `analyze_credit_spread` let `NaN` bid/ask/IV silently reach `optionlab`, producing a cryptic pydantic error instead of a clear one.** When `yfinance` has no active quote for a leg it sometimes returns `NaN` (distinct from the explicit `0/0` quote fixed above) rather than a normal 0. The negligible-premium/IV guards (`short_premium <= 0.01`, `net_premium_per_spread <= 0.01`, `iv <= 0.001`) all silently pass a `NaN` through, because every numeric comparison against `NaN` in Python evaluates `False` on both sides — `nan <= 0.01` and `nan <= 0.001` are both `False`. That let `premium=nan` reach `optionlab`'s `Inputs` model, whose `strategy` field is a discriminated union (`Stock | Option | ClosedPosition`); pydantic then failed to cleanly match the leg dict against any single variant and raised an 8-error validation blob spanning all three variants (`Stock.type`, `Option.premium`, `ClosedPosition.type`/`prev_pos`) instead of one legible message — the real signal (`Option.premium ... Input should be greater than 0 [input_value=nan]`) was buried in the middle of it. Now explicitly checked with `math.isnan()` on `short_premium`/`long_premium`/`iv` right after they're computed, before any of the existing guards, returning a normal `{"error": "No market data..."}` response instead.
- **Two-pass cycle** (`traders.py: Trader.run_agent_two_pass`, options traders only): unlike other traders' single `Runner.run` call per cycle, Cathie runs `close_positions_message` (review/close existing positions) and `new_trades_message` (research + open new spreads) as two independent `Runner.run` calls, each with its own turn budget (`CLOSE_PASS_MAX_TURNS`/`TRADE_PASS_MAX_TURNS`, 20/45). Her combined workflow -- position review plus evaluating 3-5 candidates at ~4-6 tool calls each -- was routinely exceeding a single shared `MAX_TURNS` (originally 30, tuned for the simpler one-symbol stock-trading template). Splitting means one pass running long doesn't cost the other its progress; pass 1's `final_output` (or a placeholder if it errored/exhausted its turns) is threaded into pass 2's prompt so the single end-of-cycle push notification can still summarize both.
- **Dashboard** (`app.py`): Cathie gets an options-specific panel (cash/premium-collected/open-risk breakdown, a positions log table, live unrealized P/L fetched from `yfinance` in `get_options_summary`) instead of the stock holdings/transactions tables other traders would get. Her headline portfolio-value number and chart (`Trader.get_portfolio_value`/`get_portfolio_value_chart`) track her options account's live `cash` directly rather than the untouched stock `Account` -- that stock account is a separate $10,000 pool she never actually trades, so using it (as other traders' dashboards do) would either stay flat forever or double-count starting capital if blended in. `traders.py: Trader.run()` records the same options-cash figure into the (stock account's) `portfolio_value_time_series` field each cycle, so the chart's existing storage plumbing didn't need to change, only what value gets written to it.
- yfinance and OptionLab need no API key (free); see the dependency note above for installing them.
