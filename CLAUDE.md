# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository shape

This repo currently holds two unrelated, independently-runnable projects, plus a couple of stray scripts:

- **Root (`app.py`, `requirements.txt`, `foundations/`)** — the deployed Hugging Face Space: a Gradio chat app where an LLM answers questions in character as the repo owner, using their LinkedIn profile/summary as context (`foundations/app.py`, class `Me`). This is intentionally minimal — a previous restructuring ("HF deploy") stripped the rest of the original course repo (the numbered `1_foundations`...`5_autogen` lab folders and their `community_contributions`) down to just this, to keep the deployed Space small.
- **`6_mcp/`** — a separate, self-contained project: an autonomous agent-driven paper-trading floor (currently a single trader, Cathie, who trades options credit spreads). Deliberately kept out of the HF-deploy trim (unlike the other numbered folders) because it's the active project. Everything below is about this directory.
- `LEANscriptOptionsbacktest.py`, `pdf_to_text.py` — standalone one-off utility scripts at root, unrelated to either app above.

`6_mcp/community_contributions/` (a grab-bag of unrelated student/community submissions bundled with the original course material) has been removed. There is no root README, no lint config, and no test suite.

## Running things

**HF chat app** (root): `python app.py` — needs `OPENAI_API_KEY`; reads `foundations/me/ProfileLinkedin.txt` and `foundations/me/summaryRJ.txt`.

**Trading floor** (`6_mcp/`), each run from inside `6_mcp/`:
- `uv run reset.py` — resets Cathie's stock account (cash/strategy text; she never actually trades stocks, see below) back to its starting balance (wipes prior state).
- `uv run reset_cathie_options.py` — separately resets Cathie's *options* account (`cathie_options` in `accounts.db`): clears open/closed spread positions and resets cash to $10,000. Run this too when you want a clean slate, since options positions live in a separate pseudo-account from the stock one `reset.py` touches.
- `uv run trading_floor.py` — starts the scheduler: runs every trader once, then sleeps `RUN_EVERY_N_MINUTES` (default 60) and repeats. Skips runs while the market is closed unless `RUN_EVEN_WHEN_MARKET_IS_CLOSED=true`. Only one instance can run at a time against a given checkout -- a second launch fails fast with a clear error instead of silently running alongside the first (see "Fixed: nothing stopped two `trading_floor.py` processes..." below for why that matters).
- `run_trading_floor.ps1` (Windows/PowerShell only) — wrapper around `uv run trading_floor.py`: logs timestamped start/crash/restart events to `logs/trading_floor_wrapper.log` (appended across restarts) and auto-restarts up to 3 times (30s apart) if it exits nonzero, since the scheduler above is meant to run forever and any exit during normal operation is a crash. A manual Ctrl+C stops the whole wrapper rather than triggering a retry (PowerShell's default behavior) -- **but observed live not to reliably kill `trading_floor.py`'s child MCP-server subprocesses on Windows** (`accounts_server.py`, `push_server.py`, etc. -- Windows doesn't cascade-terminate a process tree by default the way POSIX signal groups do), leaving them orphaned and still running even though the single-instance lock (see below) correctly let a fresh launch through right after. After any Ctrl+C, verify nothing's left before restarting: `Get-CimInstance Win32_Process -Filter "Name = 'python.exe'" | Where-Object { $_.CommandLine -like "*.venv\Scripts\python.exe*" }` -- kill anything it still lists (`Stop-Process -Id <PID> -Force`) rather than assuming Ctrl+C fully cleaned up. Purely a convenience for unattended Windows runs -- `uv run trading_floor.py` directly works everywhere and is what this wrapper calls.
- `uv run app.py` — Gradio dashboard visualizing account state/logs across traders.
- `python install_options_deps.py` — installs `yfinance`/`optionlab`/`scipy` (the options system's dependencies; not needed by anything else in `6_mcp/`).
- `uv run schwab_auth_setup.py` — one-time (well, recurring every ~7 days) interactive login to Schwab, needed only if you want Cathie's options tools to use real Schwab market data instead of yfinance; run from a machine with a real browser, not the scheduler. Optional -- everything works on yfinance alone without it. Use `uv run`, not a bare `python` on your PATH -- `schwab-py` is installed into this subproject's `.venv` via `uv sync`, not necessarily onto whatever interpreter a plain `python` resolves to. See "Schwab market data" below.
- `uv run schwab_account_check.py [--match AMOUNT ...] [--days N]` — read-only check of your real Schwab account through the Trader API (masked account number, type, every balance field, option positions, recent orders). Step 1 of live trading; see "Live trading on Schwab" below. Needs the "Accounts and Trading Production" API product on the Schwab app.
- `uv run schwab_order_dryrun.py SYMBOL bull_put|bear_call SHORT LONG YYYY-MM-DD [CONTRACTS] [--credit X]` — step 2 of live trading: builds a real NET_CREDIT spread order from Schwab's own contract symbols, shows the real-money risk checks against live balances, and asks Schwab's previewOrder endpoint to validate it. Never sends the order.
- `uv run schwab_order_smoketest.py SYMBOL bull_put|bear_call SHORT LONG YYYY-MM-DD [--send]` — step 3 of live trading: **sends one real order** (with `--send` plus typing SEND), priced so it can't fill, waits while you find it in thinkorswim, then cancels it and confirms. Without `--send` it only shows the plan.
- `uv run approve_orders.py [--list | --exits]` — step 4 of live trading (only matters with `CATHIE_EXECUTION_MODE=approve`): updates the real-trade ledger from Schwab, then shows each trade Cathie staged, re-checked live, and asks y (send) / r (reject) / Enter (skip). `--list` only shows the ledger. `--exits` is a dry run of step 5's automatic exit check: for each open real position, which exit rule it meets right now and at what price it would be closed; sends nothing. Creating a file named `STOP_TRADING` in `6_mcp/` blocks all real staging and sending, automatic closes included.
- `uv run spread_scanner.py [--explain TICKER ...]` — runs the code-driven credit-spread scan by hand and prints the top qualifying spreads (`--explain` instead shows, per ticker, how many candidate spreads each rule rejected, its next earnings date, and whether it's one of the user's own underlyings) (the same scan the trading floor runs before every new-trade pass; see "Spread scanner" below). Read-only, needs Schwab market data, takes a few minutes for ~300 tickers.
- `uv run tradealgo_scraper.py login|discover|fetch` — scrapes dark-pool data from the user's own TradeAlgo account (see "TradeAlgo dark-pool scraper" below). Runs on the user's machine, independent of the trading floor; `uv run playwright install chromium` once first.
- Individual MCP servers (`accounts_server.py`, `push_server.py`, `market_server.py`, `regime_server.py`, `options_trading_wrapper.py`) are not run directly — they're launched as subprocesses over stdio by the trading floor per `mcp_params.py`.

`6_mcp/pyproject.toml` + `uv.lock` declare/pin the subproject's dependencies (including `yfinance`/`optionlab`/`scipy`, previously undeclared anywhere) -- restored after being removed along with the rest of the original course scaffolding in the HF-deploy restructuring; `uv run <script>.py`/`uv sync` from inside `6_mcp/` now resolve and sync a `.venv` from that lock rather than falling back to ad-hoc-script mode. `python install_options_deps.py` still exists and still works as a standalone manual-`pip install` path for anyone managing their own environment directly instead of through uv (e.g. `python <script>.py` against an existing venv they already maintain by hand) -- both are equally supported ways to run this subproject, pick whichever fits how you're already working. Note that the trading floor's own MCP-server subprocesses (`accounts_server.py` etc.) are deliberately launched with `sys.executable`, not `uv run`, regardless of this manifest -- see `mcp_params.py`'s `PYTHON` comment; that's about guaranteeing the exact same interpreter/env as the parent process, not about the lock file.

**Fixed: `mcp` was unpinned in `pyproject.toml` and had locked to `2.0.0`, which breaks every local MCP server in this subproject.** `mcp` 2.0.0 restructured `mcp.server` and dropped the `mcp.server.fastmcp.FastMCP` import path that `accounts_server.py`, `push_server.py`, `market_server.py`, `regime_server.py`, and `options_trading_server.py` all use to define their tools -- importing any of them raised `ModuleNotFoundError: No module named 'mcp.server.fastmcp'` outright, so a fresh `uv sync` on this lock could not run any server, the trading floor included. `uv.lock` had this exact version pinned (not something that changed underfoot -- resolving is deterministic), so this was silently broken for anyone syncing fresh rather than reusing an older, already-populated `.venv`, since the last time `uv.lock` was regenerated. Now pinned `mcp<2.0.0` in `pyproject.toml` (relocks to `1.29.0`, the newest 1.x compatible with `openai-agents` 0.21.1's own `mcp` requirement) and re-locked -- worth relocking again the normal way (drop the upper bound) once `openai-agents` itself picks up `mcp` 2.x support, rather than leaving this pin in place indefinitely.

## Architecture: the trading floor (`6_mcp/`)

A single trader persona, Cathie (named for Cathie Wood; aggressive crypto ETF bets), runs each cycle (`trading_floor.py` → `traders.py`). The floor originally ran four personas (Warren/Buffett-value, George/Soros-macro, Ray/Dalio-risk-parity, plus Cathie); the other three were removed to simplify things, but `traders.py`/`trading_floor.py` still support an arbitrary list of traders via `names`/`lastnames`/`model_names` — add entries there and a matching strategy in `reset.py` to bring more traders back.

Persona strategy text lives in `reset.py`; it's injected verbatim into the agent's prompt (`templates.py`) alongside live account state.

Cathie's named ETF universe (`universe.py: CATHIE_ETF_UNIVERSE`) is the one place that list of tickers is defined; `reset.py`'s strategy text and both `templates.py` prompts (`trader_instructions`, `new_trades_message`) all interpolate it rather than hand-copying their own list -- they used to, and the copies had already drifted apart (one silently dropped four tickers). Her Researcher sub-agent gets explicit instruction (in both `researcher_instructions` and the trader-facing prompts) to check its per-trader memory for recently-suggested underlyings and favor genuinely different candidates over defaulting to the same familiar few -- prompt steering only, same caveat as everything else non-server-enforced in this file.

- **Model selection**: Cathie uses `gpt-4o-mini` by default, overridable via `MODEL_NAME` (`trading_floor.py`). Any plain OpenAI model name (e.g. `gpt-4o`, `gpt-4.1`) needs no code change, just the env var — `traders.py: get_model` passes it straight through to `Agent(model=...)`. Names containing `deepseek`/`grok`/`gemini`, or containing `/` (routed to OpenRouter, e.g. `anthropic/claude-...`), get dispatched to the matching client instead — those need the corresponding `*_API_KEY` set (see `traders.py` top). A model swap alone doesn't guarantee more trades: her low trade frequency could equally be the ~18-ticker named universe plus news research repeatedly failing to surface enough candidates that clear the server-enforced gates (25–45 DTE, delta under 0.20, premium floor, max-loss cap), independent of which model is reasoning about them — see `get_stock_screener` below, added to widen candidate supply as the more targeted fix for that.
- **Two tool surfaces per trader** (`traders.py: Trader.create_agent`): its own "trader" MCP servers (accounts, push notifications, market data, and — Cathie only — the regime signal tool), plus a `Researcher` sub-agent exposed as a callable `Tool`, which has its own MCP servers (web fetch, Brave search, and a per-trader libsql memory store) for qualitative news research (`mcp_params.py`). `traders.py` itself also reads the accounts server directly each cycle (account report, strategy text) via `accounts_client.py`, outside of the LLM's own tool calls; it does this through the same persistent `accounts_server` connection already open for the cycle (looked up by name off `trader_mcp_servers`, see `run_agent`), rather than `accounts_client.py` spawning a fresh subprocess+handshake per read — `accounts_client.py`'s functions still support the latter as a fallback for one-off calls outside a trading cycle (e.g. from a notebook).
- **Trade vs. rebalance**: `Trader.run()` alternates each cycle between `trade_message` (look for new opportunities) and `rebalance_message` (review existing positions), via the `self.do_trade` flip (`templates.py`). Options traders (Cathie) are the exception -- see below.
- **Persistence**: account state and logs live in a local SQLite DB (`database.py`, `accounts.py`), read/written concurrently by `trading_floor.py` and the `app.py` dashboard when both run at once.
- **Scheduler robustness**: `trading_floor.py`'s main loop and `traders.py: Trader.run()`'s post-cycle portfolio-value recording (`Account.get`/`read_account`/`account.save`, all SQLite I/O) both fail safe on error now rather than crashing the whole process -- `is_market_open()` (`market.py`) catches Polygon errors and reports the market closed for that cycle; the portfolio-value tail catches its own errors (e.g. a locked DB from the dashboard's concurrent access) and just skips that cycle's chart data point. Both used to be unguarded code sitting directly in the scheduler's per-cycle path outside any trader-level try/except, so either one throwing took the entire floor down permanently until manually restarted.
- **Fixed: nothing stopped two `trading_floor.py` processes from running concurrently, which is worse than it sounds.** Reproduced live: a leftover instance from an earlier restart kept running alongside a new one, unnoticed, for over a day. Both raced on the same `schwab_token.json` with no file locking on either side (schwab-py's own token writer has none), which looked exactly like Schwab market data flaking after ~1 cycle every time -- one process's write landing mid-read/mid-write of the other corrupted what the other saw, even though the token itself was fine and nowhere near its real 7-day expiry. That's the more visible symptom, but the real problem is worse: two live instances also means Cathie's account state in `accounts.db` was being driven by two independent trading cycles at once, risking duplicated trading activity, not just a data-source problem. `single_instance.py` now takes a real OS-level file lock (`msvcrt` on Windows, `fcntl` on POSIX, held for the process's whole lifetime and released automatically on any exit -- clean, crashed, or killed) at the top of `trading_floor.py`'s `__main__` block; a second launch now fails fast with a clear message naming the conflict instead of silently running alongside the first.
- **Market data tier**: `market.py` picks between free EOD-only, paid 15-min-delayed, or realtime data based on `POLYGON_PLAN`; the "market" MCP server swaps between a local `market_server.py` (free tier) and the full `mcp_polygon` package (paid/realtime), per `mcp_params.py`.
- **Tool-call visibility**: every tool call (any MCP tool, plus the Researcher sub-agent itself, since it's exposed to the trader as a callable tool) shows up in `app.py`'s dashboard log panel as a one-line `Called <tool_name>` entry (`tracers.py: LogTracer`, span type `"function"`) — added after the dashboard's `SHOW_TYPES` filter was found to silently hide that span type entirely, making it impossible to tell from the dashboard whether e.g. `get_stock_screener` or `get_market_regime` ever actually got called. `LogTracer` now logs function spans once, on completion, rather than on both start and end like other span types, since a whole Cathie cycle can rack up 20-30+ tool calls and doubling that row count would crowd everything else out of the dashboard's fixed-size log window (bumped from 50 to 150 rows at the same time for the same reason). This only reflects a tool being *called* — it says nothing about whether the call succeeded or was rejected (e.g. a `sell_credit_spread` rejection is an ordinary `{"error": ...}` return value, not a span error), so it complements rather than replaces reading `get_options_positions()`/the DB for real outcomes.
- **Cathie's Researcher and options prompts now require certain tool calls rather than merely suggesting them** (`templates.py`: `trader_instructions`, `new_trades_message`) — `get_stock_screener` (once per new-trade pass, any query) and `get_market_regime` (once per seriously-considered candidate) were previously framed as optional/"if you want to look beyond that", which the LLM was observed skipping most cycles; both are now marked MANDATORY alongside the existing non-negotiable rules. Still prompt-only, not server-enforced — there's no code path that rejects a cycle for skipping them, only the same "worth spot-checking real behavior" caveat as everything else in this file that isn't backed by a tool-side check. `TRADE_PASS_MAX_TURNS` bumped 45 -> 55 (`traders.py`) to give the extra mandatory calls headroom within the pass's turn budget.

**Spread scanner (`spread_scanner.py`), added 2026-10-08.** Root cause it fixes: given ~240 screener tickers plus the watchlist and dark-pool lists, Cathie was told to "check 3-5 candidates" with `get_options_chain`. The screener rows (symbol/price/volume) gave her nothing to tell AMD from the rest, while the watchlist and dark-pool prompts were worded strongest. So she only ever chained watchlist and dark-pool names, and missed viable screener names: the user found AMD and MU in thinkorswim with $100+ premium, good OI and delta, exp 11/06. Prompt wording couldn't fix a ~300-chain mechanical screen, so it's code now:
- **When it runs.** `traders.py: run_agent_two_pass` calls `spread_scanner.scan()` (in a thread, best effort) after the position-review pass and before the new-trade pass. Its result goes into `new_trades_message(..., scan_report)` via `templates._scanner_section`. A one-line summary is logged as type `scan` (shown on the dashboard) and printed.
- **Candidates**, de-duplicated, scanned in priority order: watchlist, TradeAlgo dark-pool (intraday and historical), `CATHIE_ETF_UNIVERSE`, then all six Yahoo screens (40 each, $50+ via `MIN_SCREENER_PRICE`). Each candidate is tagged with its `sources`.
- **Per ticker:** one Schwab chain call for 25-45 DTE, `strike_count=40` (new optional arg on `schwab_client.get_option_chain`), 4 worker threads behind the shared rate limiter. A 360s time budget stops new tickers and reports a partial scan.
- **Rules (user chose all recommended defaults, 2026-10-08).** Bull puts and bear calls, $5 and $10 wide; short |delta| <= 0.20; bid and ask on both legs; OI >= 100 on both legs; natural no more than 10% of the spread's width below mid (was 25% of the mid until 2026-10-08, see below); $50+ premium at the mid; max loss <= 5x premium and <= 8% of Day Net Liq when the account is readable. Keeps the best spread per ticker and direction, ranked by premium/max loss; top 10 go to Cathie.
- **Earnings** (`options_trading_server._get_next_earnings_date`, only for tickers that produced a spread) drops anything with earnings from today through 20 days past expiration. In approve mode it also drops unknown earnings and the user's own underlyings, which staging would reject anyway.
- **Schwab only.** Without Schwab, the scan reports `skipped` and the prompt falls back to the old by-hand routine (six screener calls, 3-5 `get_options_chain` checks).
- **Prompt changes.** The six mandatory `get_stock_screener` calls and the mandatory `get_custom_watchlist` call were dropped from `new_trades_message` and `trader_instructions` when the scanner runs; its results already cover those sources. `get_dark_pool_activity` (for direction) and `get_market_regime` per candidate stay mandatory. Cathie is told to check each scanned spread's direction against her research, regime and dark-pool flow, then analyze/sell with exactly those strikes. When nothing qualifies, the expected outcome is no trade.
- **Prices are mids for 1 contract;** `sell_credit_spread` and (in approve mode) `approve_orders.py` still re-check everything. Tested against a fake chain/screener/account. **First live run** (2026-10-08, after hours, approve mode): 132 unique candidates (the six screens overlap heavily, and the $50 floor trims them), all scanned in 73s with 0 chain errors. CIEN and SNDK were skipped as the user's own; 15 tickers were dropped for earnings (mid earnings season). The likely reasons are earnings for AMD (it usually reports in early November) and the wide after-hours quotes. **Shared entry rules (`trade_rules.py`), added 2026-10-08 at the user's request.** The scanner's first live run surfaced PENG (~$72.61) with a bull put 60/55 on its own earnings day. The user wouldn't take it: too small and volatile a stock for a $5 cushion, and a fresh report is a red flag. The forward earnings rule couldn't see this: once a company reports, yfinance's calendar shows the NEXT date. **Cathie's regime-signal tool** (`regime_signal.py` / `regime_server.py`, wired in via `mcp_params.py: TRADERS_WITH_REGIME_TOOL`) is a quantitative addition on top of the otherwise fully LLM-reasoning-driven traders:
- Labels each day Bull/Sideways/Bear from a *rolling* 20-day cumulative return (needs a rolling window to have a live "today" label).
- Fits the transition matrix from *non-overlapping* 20-day strides rather than daily — adjacent rolling windows share 19/20 days of underlying data, so counting daily transitions as independent samples overstates confidence (pseudo-replication).
- Forecasts N-days-ahead regime probabilities via true matrix exponentiation (`numpy.linalg.matrix_power`), not by squaring a single scalar probability — squaring a scalar silently assumes zero autocorrelation, which contradicts the tool's own "stickiness"/persistence concept.
- Reports an explicit `confidence` label tied to transition-matrix sample size, and refuses to return a signal at all below a minimum history threshold rather than guessing.
- It's framed to Cathie (in her `reset.py` strategy text and `templates.py` instructions) as a *lagging* trend-context signal to weigh alongside her news research when picking directional bias — not a standalone buy/sell instruction, and not a profitability guarantee.
- **Fixed: `get_historical_closes` bypassed `market.py`'s shared Polygon rate limiter entirely**, calling `client.get_aggs()` on its own fresh `RESTClient` instead of going through `market.py: _polygon_rate_limited_call` (which every other Polygon caller in the process -- `is_market_open`, share-price lookups -- already queues behind, to stay under the free tier's 5-requests/minute cap). That was always a latent race, but became a reliable `429 Too Many Requests` once `get_market_regime` went from optional to MANDATORY per-candidate (see below): 3-5 candidates in one new-trade pass means 3-5 Polygon calls in quick succession, on top of whatever else the cycle was already making. Now routed through the same shared limiter, so regime calls queue instead of racing -- at the cost of the new-trade pass running slower (each queued call can wait up to ~60s) when evaluating multiple candidates back-to-back on the free tier. The limiter's 5-req/min cap is hardcoded regardless of `POLYGON_PLAN`, so this is unnecessarily conservative for anyone on a paid/realtime plan -- not addressed here, out of scope of this fix.

**Cathie's options credit-spread system** is her actual trading mechanism — she does not buy/sell stocks at all (`templates.py: trader_instructions` forbids it explicitly; enforced by instruction, not by removing her `accounts_server` access, since she still needs `get_balance`/`change_strategy`). It's a separate, more substantial subsystem:
- **`options_models.py`** — `CreditSpread`/`OptionLeg`/`OptionsAccount` pydantic models. Positions are tracked in a pseudo-account named `cathie_options` in the same `accounts.db` (via `database.py: read_account`/`write_account`), completely separate from her real `cathie` stock `Account` (which stays untouched at its starting balance, since she never trades stocks).
- **`options_trading_server.py`** (run via `options_trading_wrapper.py`, an MCP-tool wrapper) — eight tools: `get_custom_watchlist`, `get_dark_pool_activity` (TradeAlgo dark-pool data -- see "TradeAlgo dark-pool scraper" below), `get_stock_screener`, `get_options_chain`, and `analyze_credit_spread` (read-only: `get_custom_watchlist` reads the user's own hand-edited `watchlist.txt` -- see below; `get_stock_screener` pulls a live list of actively-traded stocks from Yahoo Finance's screener via `yfinance.screen`, as extra unverified candidates beyond `universe.py`'s named ETF list; the other two get real chains/Greeks (Schwab when configured, yfinance + `optionlab`'s Black-Scholes otherwise -- see "Schwab market data" below) and P/L/probability-of-profit via `optionlab`), `sell_credit_spread` and `close_credit_spread` (mutate `cathie_options`), `get_options_positions` (read it back). Only trades **bull put** and **bear call** credit spreads — defined-risk, premium-selling strategies — never naked options.

- **Fixed bug: `close_credit_spread` trusted a 0/0 bid-ask quote as a real $0.00 closing cost.** The profit-capture check (`closing_cost <= 25% of premium`) used whatever `yfinance` returned for the short/long legs without checking it was a real quote. `yfinance` returns `bid=0, ask=0` when no market maker has an active price -- routine outside regular trading hours, or for a thin/deep-OTM strike -- not proof the option is actually worthless. That meant a stale overnight quote could silently compute a fabricated $0.00 closing cost, which trivially satisfies the 75%-captured rule and force-closes a position that was never verified against a real price. At least two live positions closed for suspiciously "perfect" $0.00 cost shortly after opening, both outside regular trading hours (no real session elapsed in between) -- the kind of theta decay that would take weeks, not hours, on a 25-45 DTE spread. Now requires at least one nonzero side (bid or ask) on *each* leg before trusting the quote; otherwise falls through to the existing "no market data" handling, which assumes breakeven rather than fabricating a gain. This does not retroactively correct any already-closed position's recorded P&L in the DB -- those entries stand as recorded unless manually corrected.
- **Fixed: NaN option quotes could slip past every server-side gate.** yfinance returns pandas `NaN` for missing quote fields, and `_fetch_chain`'s old `float(x or 0.0)` idiom let it straight through, since NaN is truthy. Every gate here is a comparison, and comparisons against NaN are always False, so a NaN value skips checks instead of tripping them. Reproduced against the old code with a mocked chain: a position breaching its short strike, with a NaN bid on the short leg, got *closed* by `close_credit_spread` with `closing_cost` and `realized_pnl` both recorded as `$nan` in `cathie_options`. The NaN quote passed the 0/0-quote guard above via the leg's other, real side. The *open* path was already blocked, but only by accident: OptionLab's own `Inputs` validation (`premium > 0`) rejects NaN, with a cryptic pydantic error. Now: `_fetch_chain`'s yfinance rows map NaN bid/ask/lastPrice to `0.0` and NaN IV/volume/openInterest to `None` (`_finite_or`), and explicit `math.isfinite` guards were added as defense in depth against any data source. The guards cover leg premiums, IV, and underlying price in `analyze_credit_spread`; net premium and max loss in `sell_credit_spread` right before the account mutation; and every leg quote plus the underlying price in `close_credit_spread`, where a non-finite quote now counts as "no market data" instead of a real price. This does not retroactively fix any already-recorded NaN P&L in the DB; check `get_options_positions()` for `NaN`/`nan` values in closed positions if in doubt.

The floor was running overnight because `RUN_EVEN_WHEN_MARKET_IS_CLOSED=true` was set; the user has since turned that off. Two fixes in `close_credit_spread`. (A) Breach and profit exits now only act during the regular session (`_regular_session_open`: Mon-Fri 9:30-16:00 America/New_York, via `zoneinfo` + the already-locked `tzdata`). Outside it they're held: the rejection says which rule would apply at off-hours prices and to re-check during market hours. The 7-day rule is date-only, so it still closes at any hour. The clock check doesn't know exchange holidays or early closes, so a holiday weekday counts as open. (B) The rule that actually justified a close is now recorded server-side: `close_rule` and `underlying_price_at_close` on the `CreditSpread` record (new optional fields; older records read as `None`), and in the `write_log` entry alongside the ET time, price source and the model's stated reason (labelled as such). That note is still prompt steering, same caveat as the "narrating a rejection as a success" gap above. The ORCL close itself stands in the ledger as recorded.
- **Two-pass cycle** (`traders.py: Trader.run_agent_two_pass`, options traders only): unlike other traders' single `Runner.run` call per cycle, Cathie runs `close_positions_message` (review/close existing positions) and `new_trades_message` (research + open new spreads) as two independent `Runner.run` calls, each with its own turn budget (`CLOSE_PASS_MAX_TURNS`/`TRADE_PASS_MAX_TURNS`, 20/90 -- `TRADE_PASS_MAX_TURNS` bumped from 45 as `get_stock_screener`/`get_market_regime` went from optional to mandatory, then again as `get_stock_screener` went from one mandatory call to six). There's no way around this from the unattended scheduler (`trading_floor.py`'s every-N-minutes loop) -- it's a recurring manual chore for whoever runs this, not a one-time setup.

  - **Root-caused: `refresh_token` missing from the token file is genuinely Schwab-server-side behavior, not a bug in this repo, `schwab-py`, or `authlib`.** Symptom: real Schwab data worked for exactly one cycle after `uv run schwab_auth_setup.py`, then every subsequent cycle fell back to yfinance forever, with `schwab_token.json`'s `token` object confirmed (by inspecting its keys directly, never its values) to have `access_token`/`expires_at` but no `refresh_token`. Traced the entire write path in both libraries' source line by line -- `authlib`'s `fetch_token()`/`parse_response_token()` does `token = resp.json()` verbatim with no field filtering (true in both 1.8.0 and 1.7.2), and `schwab-py`'s `client_from_received_url()` only wraps that same dict as `{"creation_timestamp": ..., "token": token}` before writing it -- neither library drops or transforms any keys anywhere in the chain. Confirmed directly with a standalone script that bypasses both libraries entirely and POSTs to Schwab's token endpoint (`https://api.schwabapi.com/v1/oauth/token`) with plain `requests`: Schwab's raw JSON response **did** include `refresh_token` for a login done right after revoking the app's access. Per Schwab's own docs and corroborating reports (schwab-py's `docs/auth.rst`, community writeups), **Schwab only issues a `refresh_token` on a genuinely fresh authorization grant** -- re-running the OAuth login flow against an app that already has a live, unrevoked grant for that account returns a token response with no `refresh_token` at all, by design, not as an error. Every earlier re-login in this repo's troubleshooting history was done without revoking first, which is exactly why it kept recurring. **Fix**: before re-running `uv run schwab_auth_setup.py` to get a token with a real `refresh_token`, go to `client.schwab.com` → account → Security Settings → **Linked Apps and Websites**, find the app (e.g. "getOptionsChain") under "Companies With Access to Your Account Information", and click **Stop Linking** to revoke it first -- *then* log in again by running `schwab_auth_setup.py` (its own browser-based Allow flow *is* the relink -- no separate manual "link" step exists, and it takes effect immediately, no waiting period). Routine 7-day refresh-token expiry (see above) does not require this extra revoke step first; only a re-login done *before* the refresh token has actually expired does, since the old grant is still live on Schwab's side in that case. **Confirmed live end-to-end**: revoking via "Stop Linking" and immediately re-running `schwab_auth_setup.py` produced a token file with `refresh_token` present, closing this out. Do not use developer.schwab.com's "Deactivate App" for this -- that deactivates the app's own registration/credentials entirely, a different and unrelated action.
  - Rate-limited similarly in spirit to `market.py`'s Polygon limiter (reserve a slot, wait rather than hammer the API, raise `TimeoutError` past a bounded wait rather than hang past the caller's own MCP client timeout) -- Schwab doesn't publish one official number the way Polygon does, so the cap here (100 calls/62s) is a conservative estimate, not a documented guarantee.
  - **Verified against live Schwab traffic** (developer.schwab.com app "getOptionsChain"): the manual OAuth login (`uv run schwab_auth_setup.py`) completed end-to-end and wrote a working token file, and a direct `schwab_client.get_option_chain("SPY", ...)` call returned a real chain -- genuine bid/ask, open interest, IV, and per-contract Greeks (delta/gamma/theta/vega), not placeholders. Confirms both the OAuth flow and the Market Data API entitlement work in practice, not just in code review.
  - **Fixed: turning Schwab on reintroduced the same context-window overflow `get_stock_screener` had (see above) -- reproduced live the first time a real trading cycle ran against a working Schwab connection.** `get_options_chain`'s per-strike listing previously included gamma/theta/vega whenever a record had them, which in practice meant "never" (yfinance has no Greeks at all beyond delta, computed separately via Black-Scholes) until Schwab actually started working -- at which point it meant "always, with real non-null values," across up to 50 strikes per call and up to 2 calls per candidate. None of Cathie's rules ever check gamma/theta/vega at this per-strike level (only delta, for the 0.20 band, and open interest/premium) -- the fuller Greeks for her actual chosen spread are already in `analyze_credit_spread`'s output, one spread at a time, not up to 50 strikes. Now drops gamma/theta/vega from `get_options_chain`'s per-strike listing unconditionally (not just when null) and rounds the remaining floats, keeping its payload roughly the same size regardless of which data source supplied it.
  - **Fixed: Schwab's `-999.0` "not computable" sentinel was passed through as a real Greek/volatility value.** Schwab's chain endpoint reports `-999.0` (occasionally `"NaN"`) for `delta`/`gamma`/`theta`/`vega`/`volatility` on contracts it can't price -- typically ones with no live quote. `schwab_client.py` copied those straight into its normalized rows, so `get_options_chain` could show Cathie a delta of `-999` and `analyze_credit_spread`'s Schwab-Greeks branch would fold `-999` into its net gamma/theta/vega. The server-enforced gates happened to fail closed on it (`|delta| > 0.20` rejects; IV of `-9.99` trips the zero-IV guard), so no bad trade could open -- but the numbers shown to the model were nonsense. `get_option_chain` now maps any non-numeric, NaN, or `<= -999` Greek/volatility value to `None`, which every caller already handles (Black-Scholes fallback in `analyze_credit_spread`, missing-delta rejection in `sell_credit_spread`). Found in pre-merge review of PR #11, not observed live yet.

## TradeAlgo dark-pool scraper (`6_mcp/tradealgo_scraper.py`)

Pulls dark-pool data from the user's own logged-in TradeAlgo account as an extra research signal for Cathie. **Permission status:** TradeAlgo support informally OK'd automated access to data already visible in this account, for a private trading bot, at once or twice a day. That's informal, not a formal agreement, and it defines the scope: own session only, own account's data only, and at most 2 fetches per calendar day with at least 4h between attempts. Keep the code inside that scope; don't raise the cap or widen what it reads without the user re-confirming with TradeAlgo.

- **Plain Playwright, not crawl4ai** (the tool originally considered): crawl4ai is built on Playwright, and this needs only a saved logged-in browser profile plus capturing the page's own JSON data requests (more robust than parsing the rendered page).
- **Three modes.** `login` opens a visible browser for the user to log in by hand; the script never sees the password. `discover` records which JSON requests the dark-pool page makes and the *field names/types* of each response (no values, cookies or tokens; query strings dropped; account-ID-like URL segments masked as `{id}`), written to `tradealgo_discovery.json` so it's safe to paste into a chat. `fetch` runs headless, captures the request matching `TRADEALGO_DATA_URL_CONTAINS` on `TRADEALGO_PAGE_URL`, and writes `tradealgo_darkpool.json` atomically.
- **Rate cap counts attempts, not successes**, recorded in `.tradealgo_fetch_state.json` before the request goes out, so a failing page can't turn into repeated hits on TradeAlgo's site.
- **Session cookies are saved explicitly** (`.tradealgo_profile/session_state.json`, via Playwright `storage_state`) and restored on each run. Chromium drops cookies with no expiry when the browser closes, even with a persistent profile; caught in local testing against a mock login wall that uses one. A logged-out run never overwrites a good saved session. That file holds live login cookies: treat it like a password. The whole profile dir and all TradeAlgo output files are gitignored.
- **Deliberately separate from the trading floor** (nothing in `trading_floor.py` or the MCP servers imports it; meant to be scheduled on its own, e.g. Windows Task Scheduler), so a scraper failure or expired TradeAlgo login can never stall a trading cycle.
- **Fixed: `login` crashed with a raw traceback on first live run** (`net::ERR_NAME_NOT_RESOLVED at https://app.tradealgo.com/`). That default address was a guess made from this sandbox, which can't reach TradeAlgo at all, and the domain doesn't exist. There's no built-in default any more. If `TRADEALGO_HOME_URL` is unset, or its address won't load, `login`/`discover` print a plain note and leave the browser window open for the user to type their usual TradeAlgo address. `login` then saves that site's origin to `.tradealgo_profile/home_url.txt` for later runs. The failed tab is swapped for a fresh one, because Chromium commits its own error page a moment after a failed load and that cut off the user's next navigation in the same tab (reproduced in the mock test). Pressing Enter while still on a login or error page is refused without overwriting the saved session. `discover` waits up to 10s for network activity to settle after Enter, so data requests still in flight are captured. `main()` reports any remaining browser error as one `ERROR:` line instead of a traceback.
- **Fixed: `login` refused a real login twice in a row on the user's machine** ("The browser isn't on a logged-in TradeAlgo page"), with no detail to diagnose from. Two plausible causes, both addressed. (1) Only the one tab the script opened was checked, so a login done in a new tab or a popup window was invisible. `login`/`discover` now take the most recent open tab that's on a non-login web page (`_logged_in_page`). (2) `_looks_logged_out` matched `auth` as a substring anywhere in the path, which also hits ordinary logged-in app pages (e.g. `/authenticated/...`). It now matches whole path segments only (`login`, `signin`, `auth`, `sso`, `oauth`, ...). A refusal now lists every open tab's masked address, so the next failure says what the script actually saw. Which cause it was on the user's machine is still unconfirmed.
- **Fixed (follow-up): the logged-in check no longer relies on the page address alone.** The user reports TradeAlgo's sign-in page address contains `signin`. The most likely explanation for the repeated refusals is that the address still contains it after login too, which no address pattern can tell apart from being logged out. So address matching is now only a hint. In `login`/`discover`, where the user is at the keyboard, a sign-in-looking address triggers a y/N question (`_pick_page`) instead of a refusal. `discover` no longer refuses before Enter on the start page's address. `fetch` (unattended) treats the data request actually arriving as proof of a live session, with no address check on success; HTTP 401/403 on the data request, or no data plus a sign-in-looking address, report an expired session.
- **Login and discovery confirmed live** (2026-09-29). TradeAlgo's app is `dashboard.tradealgo.com`; the user set `TRADEALGO_HOME_URL=https://dashboard.tradealgo.com/signin`. Logging in lands on `/home/Intraday/Auto/Up`, and a saved session goes straight there on later runs. `discover` found the dark-pool data behind two pages, each loaded by one JSON request on `presentation.tradealgo.com`. **Intraday** (`/home/Intraday/Auto/Up`) loads `/ats/darkflow`: `trending_up` and `trending_down`, 10 tickers each. **Historical** (`/historical/Auto/Up`) loads `/ats/historic/daily-darkflow`: a longer list (466 entries in discovery) that includes tickers flagged on earlier days. Each ticker record carries dark-pool (ATS) day trades/volume/dollar volume (current, previous, compared), options flow (put/call counts and premium, put/call ratio, flow sentiment), and TradeAlgo's AI bull/bear score.
